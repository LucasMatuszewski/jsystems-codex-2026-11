## Failure handling and smaller fallback

- Record failures in the single PR checklist with evidence and blocked dependencies. Preserve unrelated changes; no blanket staging, hard reset or checkout replacement. If a worker exceeds ownership, stop and inspect its diff before accepting anything. Retain safe useful changes separately; do not discard another author's work.
- Never commit deliberately failing Red tests in isolation: pair the verified tests and implementation in the logical Green commit. If a row cannot reach Green, leave it unaccepted and report the remaining diff. Revert only a known accepted task commit with O review; preserve dependent work and retest after reversal.
- Missing browser tooling, real provider access, safe captures or budget blocks affected live acceptance. No mocked application/E2E success, credential changes, endpoint substitution or fake screenshots. Unit/integration work may continue only where it is independently meaningful and does not invent provider response shapes.
- If time or tools are insufficient, serialize with O and reduce the live campaign to the two happy paths plus one unclear laptop/phone case. Keep both requested scenarios, real Decisions, real Luna stream, required review, key isolation and honest errors. Defer comprehensive live branch coverage and any unproven shortcut. - If real models cannot run at all, the fallback is a verified but **incomplete** local foundation and draft PR evidence, not a demonstrable finished AI slice. Publication still needs authorization. Stop before claiming T12-T14 completion.
